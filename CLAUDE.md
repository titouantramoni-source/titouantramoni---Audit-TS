## Before making any visual or layout change

Read **[`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md)** first. It is the binding art-direction brief for this site (palette, typography, spacing, composition, animation rules) and takes precedence over ad-hoc styling decisions.

`index.html` implements the current DESIGN_SYSTEM.md target: the page background is split into **three full-bleed flat color bands** (see DESIGN_SYSTEM.md §2/§11), not a single dominant kaki. In document order: `--zone-white` (`#intro`, `#cv`, `#parcours`, `#recommandations`), `--zone-cream` (`#calculateur`, `#analyses`), then `--paper` (kaki, `#personal`) leading into the black footer. Noir (`--ink`) and a bronze accent (`--bronze`, same value as `--navy`) round out the palette. Cards (`.card`/`.calc-shell`/`.cv-card`/`.edc-card`/`.reco-card`) stay on `--ivory` regardless of which band they sit in, reading as slightly lighter-than-cream / slightly warmer-than-white panels. On the kaki band (`#personal`), text switches to light colors (`--ivory`/`--muted-light`) instead of dark ink — see the `#personal`-scoped rules in the `<style>` block. The pre-kaki navy-blue variant is kept only for reference at `archive/index-original-navy.html` and should not be edited or treated as a second live version.

## What this is

A single-file personal branding site (`index.html`) for Titouan Tramoni, built to support M&A / Private Equity internship applications. It doubles as a demonstration of financial-analysis literacy (equity research write-ups, a live ratio calculator) rather than a conventional portfolio/blog.

There is no build step, no package manager, and no test suite — `index.html` is the entire deployable artifact: inline `<style>`, inline `<script>`, no external JS/CSS files. Open it directly in a browser (or serve the folder with any static file server) to view changes; there is nothing to install or compile.

## File size caveat

`index.html` is ~1MB because both CV PDFs (FR/EN) are embedded inline as `data:application/pdf;base64,...` inside `<a href="...">` attributes in two places (the hero CTA row and the "Télécharger mon CV" cards). Each base64 blob is a single physical line hundreds of KB long.

- Do not read the whole file with a generic "cat the file" approach — it will blow past normal tool/size limits. Read it in chunks by line offset, skipping the base64 lines (`grep -n 'base64' index.html` to locate them first).
- When editing HTML around a CV link, anchor the `old_string`/`new_string` on a short unique prefix of the base64 payload (or on the surrounding tag boundaries) rather than trying to match the full attribute value.
- Never regenerate or re-encode these PDFs by hand; only copy the existing base64 verbatim if it needs to move.

## Section rhythm — a non-obvious CSS gotcha

Every `<section>` nests an inner `<div class="wrap">` around its content (e.g. `<section id="parcours"><div class="wrap">...</div></section>`) rather than carrying `class="wrap"` on the `<section>` tag itself. This matters because:

- The generic `section{padding:64px 0;...}` rule provides the vertical spacing between sections, and (with no `max-width`) lets each section's own `background` paint full-bleed, edge-to-edge across the viewport.
- `.wrap{max-width:960px;margin:0 auto;padding-left:32px;padding-right:32px;}`, nested one level in, constrains just the content to a centered 960px column.

**Never put `class="wrap"` directly on a `<section>` that also sets its own `background`.** `.wrap`'s `max-width:960px;margin:0 auto` would then constrain the *section's own box* — not just its content — so the background paints only a centered 960px block instead of a full-width band, with the previous section's color showing through on both sides. This exact bug happened once (`#intro`/`#parcours`/`#analyses`/`#calculateur`/`#personal` all had `class="wrap"` on the `<section>`, so their zone-background colors rendered as inset panels rather than the intended full-screen bands like the footer's). All seven content sections (`#intro`, `#cv`, `#parcours`, `#recommandations`, `#analyses`, `#calculateur`, `#personal`) and the `<footer>` now consistently follow the nested-`<div class="wrap">` pattern — keep any new section consistent with it.

**`.wrap` must also never set a shorthand `padding` (e.g. `padding:0 32px`) or vertical `padding-top`/`padding-bottom`.** A class selector always wins over an element selector in CSS regardless of source order, so a shorthand `padding` on `.wrap` would silently zero out the section's vertical rhythm — this happened once too, producing sections that looked "stuck together" despite the `section` rule looking correct. If inter-section spacing ever looks wrong, check `.wrap`'s padding declaration first before touching the `section` rule.

**There are two separate `@media (max-width:680px){...}` blocks in the `<style>`, not one** — an early one (around the `.util-ticker`/hero rules) and a later one (right before `</style>`, currently just `.nav-drawer`). Because both target the same breakpoint, CSS resolves any selector that appears in both by plain source order: whichever occurrence comes **last** in the file wins, regardless of which media block it's in. Adding a mobile override for a class whose non-media (base) rule sits *after* the early `@media` block silently does nothing — the later base rule still wins at every width. This happened once with `.intro-columns`: the mobile 1-column override was added to the early block but the base 2-column rule lived further down, so mobile kept rendering 2 columns until the override was moved to the later block. When adding a responsive override, always add it to whichever `@media (max-width:680px)` block comes **after** that selector's base rule in the file (grep for the selector's other occurrences first) — don't assume there's only one such block.

## Navigation — hamburger menu, not a horizontal bar

The site nav is a hamburger button (`#nav-toggle`, ☰ + a visible "MENU" label — `.hamburger-icon` + `.hamburger-label`, deliberately sized up (48px tall, 28px icon) so it reads as an obvious, clickable control rather than a small ambiguous glyph) in the `.util-bar`, top-left — **not** an inline link list. `.hamburger-label` reuses the hero wordmark's typography (`'Newsreader',serif;font-weight:500;letter-spacing:.14em`, literal caps in the markup rather than `text-transform`) so the two brand-adjacent labels on the page read consistently. Clicking it opens `.nav-drawer` (a fixed-position slide-in panel from the left, `#nav-drawer`) over a `.nav-backdrop` overlay; both are toggled by the vanilla-JS block right after the calculator script (search `nav-toggle` in the closing `<script>`s). The drawer's links close it automatically on click (see the `links.forEach` handler) and `Escape` also closes it.

`.nav-drawer-brand` ("Titouan Tramoni" at the top of the drawer) is deliberately kept at the **same** `font-family`/`font-size` as `.nav-drawer a` at both breakpoints (`19px` desktop, `18px` at `max-width:680px`) — it used to be a smaller, subordinate-looking `16px`. Its only visual distinction from the links below it is a soft `text-shadow` (`0 1px 3px rgba(22,21,15,.18)`, tinted with `--ink` rather than pure black). If `.nav-drawer a`'s font-size ever changes, update `.nav-drawer-brand` to match at the same breakpoint rather than letting the two drift apart again.

`.util-bar .wrap` overrides the generic `.wrap`'s `max-width:960px;margin:0 auto` back to `max-width:none;margin:0` (keeping only the `32px` horizontal padding) so the hamburger button's left edge sits at exactly `32px` from the true viewport edge on any screen width — matching the LinkedIn/CV links in `.hero-caption`, which are full-bleed (`left:0;right:0`) with the same `32px` padding. Without this override, `.util-bar .wrap` would stay centered in a 960px column like other sections, and the hamburger would drift right of the hero links on screens wider than ~1024px. Keep this in mind if `.util-bar`'s layout changes — its horizontal alignment is intentionally pinned to the hero's, not to the rest of the page's centered content column.

`footer .wrap` carries the identical override (`max-width:none;margin:0`) for the same reason: `<div class="wrap foot-row">` would otherwise center in a 960px column too, leaving "On en parle ?" and the "Me contacter" button inset well past `32px` on wide screens instead of flush with the true left/right edges like the hero links and hamburger. Any section whose content is meant to reach the true viewport edge (rather than sit in the shared 960px reading column) needs this same `max-width:none;margin:0` override on its `.wrap` — check for it if a new full-bleed section is added.

The **TradingView ticker-tape widget** (`.util-ticker`, showing live LVMH/Hermès prices) is a **separate, independent element** in the same `.util-bar` — it is not part of the nav and must never be merged with or gated by the drawer's open/close state. It's still hidden below 900px viewport width (clips its own labels otherwise — unrelated to the hamburger).

Drawer link labels/order are fixed content, not to be changed without being asked: `Accueil · Intro · Parcours · CV · Recommandations · Valorisation · Analyse Boursière · En dehors des chiffres · Contact` — matching hrefs `#accueil · #intro · #parcours · #cv · #recommandations · #calculateur · #analyses · #personal · #contact`. This mirrors the actual document order below; keep the two in sync if either changes. `#calculateur`'s nav label AND on-page `<h2>` are both "Valorisation" (renamed from "Calculateur" in the nav and "Analyse financière" in the heading, at the user's explicit request, alongside moving the section ahead of `#analyses`) — only the `id` (`calculateur`) is unchanged, see the Calculateur section below. `#analyses`'s nav label AND on-page `<h2>` are both "Analyse Boursière" (renamed from "Analyse" in the nav and "Analyses" in the heading, at the user's explicit request) — only the `id` (`analyses`) is unchanged.

## Intro animation (two kaki panels, once per session)

A full-screen opening sequence plays on the first visit of each browser-tab session: two `--paper` (kaki) panels meet along a 1px bronze line; `TITOUAN TRAMONI` sits above the line, the site's signature below it (`AUDIT & TRANSACTION SERVICES` + the tagline "Beyond the numbers. Understanding businesses."); then the line becomes the seam and the panels slide apart (top up, bottom down) onto the hero. ~2.75s after the fonts are ready. The three type voices deliberately reuse the hero's own (name = `.hero-wordmark`, signature = `.eyebrow`, tagline = hero `h1` italic), so the intro and the site read as one piece. Same palette as the page (kaki / ivory / bronze) on all four sites — no new colors.

Three pieces, all inline in `index.html`, nothing external:

1. **A `<head>` script** (right after the viewport meta, so Google Analytics stays the first thing in `<head>`) checks `sessionStorage['intro-seen:<site>']`; if unset it sets it and adds `html.intro-on`. It marks the intro as seen when it *starts*, so a reload mid-intro doesn't replay it. If `sessionStorage` is unavailable the intro is simply skipped (page stays fully usable).
2. **A CSS block** at the end of the `<style>` (`/* ---------- intro ... */`). `.intro` is `display:none` unless `html.intro-on`, so no-JS and repeat visits never see it. The whole timeline is CSS keyframes keyed off `html.intro-go` (added by JS once the Newsreader weights are loaded, max 0.9s); only `transform`/`opacity` animate, so there is no layout shift. It carries its own 6s `intro-failsafe` animation: even if every script fails, the overlay hides itself.
3. **The overlay markup + one inline script**, as the first child of `<body>` (so `Skip intro` is the first tab stop). The script only does start (`intro-go`), skip, and cleanup (`end()` removes the node and the `intro-*` classes on the top pane's `intro-open-t` `animationend`, or the overlay's own `intro-fade`; a 4.8s timer is a last-resort fallback).

**Skip:** the `Skip intro` button, a click on the overlay, `wheel`, `touchstart`, or Escape/Enter/Space/Arrow/Page keys all fade it out in ~0.35s. Never block a recruiter who wants the CV.

**Always plays — by explicit request.** It is *not* skipped for `prefers-reduced-motion` nor for deep links (`#cv`, `#parcours`…). Under reduced motion it plays a calmer variant (the `@media (prefers-reduced-motion:reduce)` block inside the intro CSS): no panel movement and no per-letter travel, just fades, ending in one overlay fade (~2.7s). Replays are prevented only by the session flag above — a new tab replays it.

Gotchas:
- **The overlay id is `intro-screen`, not `intro`** — `#intro` is the Intro *section* (nav anchor). They collided once; duplicate ids would also make `#intro` links resolve to the overlay while it exists.
- Tagline and `Skip intro` use `--ivory`, not `--muted-light`: ivory on `--paper` is ~4.6:1, `--muted-light` only ~3.7:1.
- `z-index:1000`, above `.util-bar` (20) and the nav drawer/backdrop (40/50).
- `html.intro-skip .intro{...}` must stay the **last** intro rule: it has the same specificity as `html.intro-go .intro` (reduced-motion block) and relies on source order to win.
- The name/signature fade out (`intro-fade`, 1.9s) while their panels slide, so the signature doesn't sit on top of the hero headline mid-reveal.
- Per site, only two strings and the storage key differ (`intro-seen:ma|pe|vc|at` and the signature/tagline); the CSS/JS is identical.
- **Testing caveat:** a hidden Browser pane freezes animations and throttles timers, so real-time playback can't be observed there. Verify frames by pausing and scrubbing (`document.getAnimations()` → `pause()` + `currentTime`) on a *fresh load each time* (the 4.8s fallback timer will otherwise remove the overlay mid-test), and verify the end logic by dispatching synthetic `animationend` events. `sessionStorage` is per origin — clear it on the origin you are testing.

## Parcours: scroll-driven horizontal timeline

`#parcours` has two completely different layouts gated by one combined media query, `(max-width:900px),(prefers-reduced-motion:reduce)` — used identically in the CSS (right after the `.parcours-scroller` base rules) and in the JS (`mqFallback` in the script right after the macro-bar script, near the end of `<body>`):

- **Fallback (mobile/tablet ≤900px, or reduced-motion, or JS disabled)**: pure CSS — `.parcours-panels` is a normal static block with a left spine/dot (`::before`) per `.p-panel`, exactly like the old `.timeline`/`.t-item` pattern this replaced. All five panels are always visible, in document order, full opacity. This is also what non-JS/crawler/screen-reader users effectively get, since the DOM never removes panel content — it's only ever hidden by `opacity`/positioning in the desktop-pin mode, never `display:none`.
- **Desktop pin (>900px, no reduced-motion)**: `.parcours-scroller` is a tall spacer (`height:230vh` — deliberately kept short; an earlier `380vh` made both entering and leaving the section feel like a long forced scroll and was cut by more than half after user feedback); `.parcours-pin` is `position:sticky;top:28px;max-height:calc(100vh - 28px)` (content-sized — see below — capped so it never exceeds the viewport). The `top:28px` (not `0`) is deliberate: at `top:0` the pinned title sits flush against the very edge of the browser viewport with zero breathing room while scrolling through the section — reported as looking "glued" to the browser chrome. `max-height` is reduced by the same 28px so the pin still never overflows the viewport. The script reads `scroller.getBoundingClientRect()` on scroll/resize (rAF-throttled, passive listener) to compute a 0..1 `progress`, which drives: the `.parcours-line-fill` width, which of the 5 `.p-node`s along the line have `.is-revealed`/`.is-active`, and which single `.p-panel` has `.is-active` (cross-fades via opacity/transform; only one panel is ever visually shown at a time in this mode). `progress` is continuous and reversible — there is no discrete step-lock, no `preventDefault` on wheel/scroll/touch, and nothing that can leave scrolling "stuck": the section releases the instant its bottom edge passes, exactly like any other tall element under a sticky child. If the pass-through still feels too long or too short, `.parcours-scroller`'s `height` is the one number to tune.
- The `.section-head` ("Parcours" title, class `.parcours-head`) lives *inside* `.parcours-pin` as its first child, `flex-shrink:0`, with just its default `margin-bottom`. Everything else (hint, line, panels) is wrapped in a separate `.parcours-body` (also `flex-shrink:0`, no centering). `.parcours-pin` itself is a bare flex column sized to fit its content (`max-height:100vh`, not a fixed `height:100vh`) — it used to be a fixed full-viewport box with its content vertically centered inside, which left ~250–390px of dead space above and below the actual title/timeline/panels (measured against the site's real 128px section-to-section baseline, e.g. CV→Analyses) at *both* the Intro→Parcours and Parcours→CV boundaries. Don't reintroduce `justify-content:center` or a fixed `height:100vh` on `.parcours-pin` — content should size the pin, not the other way around.
- **`.parcours-panels`'s height is JS-driven per active panel, not a fixed reservation.** Since `.p-panel` children are `position:absolute` (needed for the cross-fade), they never stretch `.parcours-panels`'s own box — it used to carry a static `min-height:358px` sized to the tallest of the 5 panels (`Aujourd'hui`, back when that panel still carried the closing paragraph + objectives list). Once that content moved out to `.p-gap`, the step-4 panel dropped to ~82px while the reserved box stayed at 358px, leaving a large dead gap between the compact "Année de césure" step and `.p-gap` right after it. `render()` now sets `#parcours-panels`'s inline `height` to `panels[activeIndex].offsetHeight` on every scroll tick (`.p-panel` elements keep real layout even while `opacity:0`, since they're never `display:none`, so `offsetHeight` is always readable); `enable()` sets `panelsEl.style.minHeight='0'` so this can go below the CSS `min-height:358px`, which now only serves as the pre-JS/no-JS safety net (and is restored, along with the inline `height`, in `disable()`). Because the cross-fade briefly shows two panels overlapping (outgoing fading out, incoming fading in, ~0.5s), a step change first sets the container to `max(outgoing height, incoming height)` and only shrinks to the incoming panel's own height via a `setTimeout(…, 520)` (slightly longer than the 0.5s opacity/transform fade) — shrinking immediately would clip the outgoing panel's fading tail exactly like the original `min-height` bug. If a panel's copy grows, no manual re-measuring is needed anymore — the height now always tracks real content automatically.
- **Gotcha**: the mobile/reduced-motion fallback resets `.parcours-pin` with `height:auto`, and separately **must** also reset `max-height:none` — the base rule uses `max-height` (not `height`) specifically so the fallback's `overflow:visible` can't be defeated by a leftover height cap. Forgetting the `max-height:none` reset caused `#cv` to overlap into the still-rendering (but layout-capped) Parcours content on mobile. If either property changes on the base `.parcours-pin` rule, check that the fallback in the combined `(max-width:900px),(prefers-reduced-motion:reduce)` block still resets *all* of that rule's sizing properties, not just the one that was there before.
- `.p-node` centers only horizontally (`transform:translateX(-50%)`, with `top:-7px` nudging the dot to straddle the line). It used to also do `translateY(-50%)` on the whole dot+date+title flex column, which centered the *text*, not the dot, on the line — visually, the line rendered through the middle of the date label. Don't reintroduce vertical centering on `.p-node` as a whole; if the dot needs repositioning, adjust `top` on `.p-node` and/or `margin-bottom` on `.p-node-dot` instead.
- The two modes are **not** just CSS visibility toggles on one JS behavior — the script itself calls `enable()`/`disable()` in response to the shared media query's `change` event (with an `addListener` fallback for old Safari), so resizing across 900px or toggling OS reduced-motion mid-session cleanly tears down the scroll/resize listeners and resets every inline style and animation class. Don't add a separate resize listener elsewhere for this section; extend `sync()` instead.
- The five steps' data lives twice in the DOM by necessity: a compact `.p-node` (date + short title) positioned along `.parcours-line` at fixed `left:0/25/50/75/100%`, and a full `.p-panel` (date, title, role, lede, missions/objectives, optional `.p-thesis`) in `.parcours-panels`. Keep both in sync if a step's date or title changes.
- The discreet "↓ Faites défiler pour découvrir mon parcours" hint (`#parcours-hint`) fades out the first time `progress` exceeds ~0.01 and does not reappear until `disable()`/`enable()` resets it (e.g. on a breakpoint crossing).
- **`.p-gap` ("Ma césure, construite en deux temps") lives inside the step-5 `<article class="p-panel p-panel--goal" data-step="4">`**, right after `.p-panel-role`, so it cross-fades in and out as part of that step exactly like every other panel — it was briefly pulled out as a sibling of `.parcours-scroller` (rendering after the pin released, in normal flow) when the step-4 panel still carried a transition paragraph + objectives list and the combined content measured ~750px, too tall for the pinned viewport; once that paragraph/list were removed (their content was redundant with `.p-gap`'s own lede) the panel dropped enough that `.p-gap` fits back inside it, even down to a 768px-tall viewport (measured via forced `.is-active` + `getBoundingClientRect()`, not guessed). This depends on `.parcours-panels`'s height being JS-driven per panel (see above) rather than a fixed reservation — with a static `min-height` this panel would need the *tallest* panel's height reserved for every step, which doesn't work once one panel is this much taller than the rest. Visually `.p-gap` is a two-column bronze-left-border phase-block layout (`.p-gap-phases`/`.p-gap-phase`/`.p-gap-phase-label`) — it was originally modeled on a similar pattern that used to live in `#personal` ("En dehors des chiffres"), but that section was since fully rebuilt (see "En dehors des chiffres: floating cards + scroll reveal" below) and no longer has an equivalent block; `.p-gap`'s classes were always its own, scoped separately, and are unaffected by that rebuild. Nested in the panel, its own top spacing (`margin-top:18px;padding-top:18px;border-top`) matches `.p-thesis`'s internal-sub-block convention rather than the larger `56px/40px` it used when it was a top-level section block. `.p-gap-phases` collapses from `1fr 1fr` to a single `1fr` column in the second/later `@media(max-width:680px)` block (per the two-680px-blocks gotcha above); in the mobile/reduced-motion fallback it just renders as part of the step-5 list item, with the same left spine dot as the other four.

## En dehors des chiffres: floating cards + scroll reveal

`#personal`'s own background (`background:var(--paper)`, the kaki band — see the zone-background rule near the top of the `<style>` block) is intentionally the one thing this section's design must never touch; everything else in it was fully rebuilt (previously a `.personal-grid` of plain text blocks with no cards).

- **`.pull-quote`** is the manifesto line, split across two visual weights in one element: the setup (`Faire confiance à un profil en construction…`) at `opacity:.82`, italic; the payoff (`<span>` — `quand je décide d'aller chercher quelque chose, je ne m'arrête pas.`) as a `display:block` line break at full opacity, non-italic, `font-weight:600`, `1.06em`. The line break, weight, opacity and size differences all point the same direction — don't rely on just one of them if this copy changes; the payoff sentence needs to visibly outweigh the setup.
- **`.edc-grid`** holds three `.edc-card` articles, `repeat(3,1fr)` on desktop, dropping to one column only at the site's existing `max-width:680px` breakpoint (gap tightens at the existing `900px` breakpoint in between — tablet just gets a narrower 3-column row, per the brief's "adapter leur largeur" ask, rather than an extra breakpoint). Cards are `background:var(--ivory)` (never pure white, same rule as every other card on the site) so they read as light objects floating on the kaki band.
- **The "floating" look is a resting shadow, not just a hover one**: `.edc-card` carries `box-shadow:0 24px 48px -18px rgba(10,10,10,.32),0 6px 16px -6px rgba(10,10,10,.16)` at rest (large, soft, low-opacity — no flat/dashboard look), a `border:1px solid rgba(150,145,106,.35)` (a translucent `--line`, needed because a white-ish border would be invisible against the ivory card itself — it has nothing to do with the kaki background), and `border-radius:6px`. `:hover` lifts with `transform:translateY(-4px)` and a slightly larger/darker shadow, both on a slow `.5s cubic-bezier(.22,.61,.36,1)` transition — deliberately gentle, no color changes, per the brief's "aucun changement brutal."
  - **Gotcha**: the hover rule is `.edc-card.edc-reveal:hover`, not the simpler `.edc-card:hover`. Both `.edc-card:hover` and the scroll-reveal's `.edc-reveal.edc-in` (below) set `transform`, and `.edc-in` sits later in the stylesheet at equal specificity (0,2,0) — the plain form would let `.edc-in`'s `translateY(0)` silently cancel the hover lift once a card has been revealed (i.e. always, since reveal fires long before a user can hover). The extra `.edc-reveal` qualifier bumps hover to (0,3,0) so it always wins. If this component's CSS grows, keep any new state rule that touches `transform` aware of this — check computed style during `:hover`, not just that the browser accepts the rule.
- **`.edc-num`** (01/02/03) is a large (`42px`) serif numeral, absolutely positioned top-right of each card at `color:var(--paper)` (the section's own kaki, tying back to it) and `opacity:.16` — a graphic watermark, not a readable label, per the brief's "peuvent être très discrets."
- **Scroll reveal** (`.edc-reveal`/`.edc-pre`/`.edc-in`, plus the script right before `</body>`): elements are `opacity:1;transform:none` by *default* — `.edc-pre` (which actually hides them, `opacity:0;translateY(18px)`) is only ever added by JS, and only when `prefers-reduced-motion` isn't set and `IntersectionObserver` exists, so content is never lost if the script fails, is blocked, or motion is reduced. Once a target's own `IntersectionObserver` fires, JS swaps `.edc-pre` for `.edc-in` (opacity/transform transition, `.7s ease`) and unobserves it — one-shot, not a persistent toggle. Read order (title → quote → cards, cards left-to-right) is enforced with explicit `transition-delay` per class/`:nth-child` rather than relying on each element's own viewport-entry timing, since on a short section or a tall viewport several elements can enter the viewport in the same frame and would otherwise reveal simultaneously instead of in sequence.
- This IntersectionObserver-based reveal is shared page-wide via the `.edc-reveal`/`.edc-pre`/`.edc-in` classes — it originally only queried `#personal .edc-reveal`, but was broadened to a plain `.edc-reveal` query specifically so the Recommandations cards (see below) could reuse it instead of duplicating the mechanism. The Parcours system nearby is unrelated and shouldn't be confused with it (continuous scroll-progress, not one-shot viewport-entry).

## Recommandations

`#recommandations` and its Parcours-embedded counterpart are both driven by one `RECOMMENDATIONS` array (in the script right before the Parcours one, so it runs — and finishes injecting into Parcours — before Parcours' own script first measures panel heights, and before the `.edc-reveal` script further down so newly-created `.reco-card` elements get picked up by it). Adding a letter later means adding one object here plus its preview image in `assets/recommandations/` (the PDF itself is embedded, see below) — and, only if it introduces a new `type`, one line in `RECO_DISCLOSURES` — never touching the CSS, the render functions, or any Parcours experience's markup.

- **PDFs are base64-embedded, matching the CV pattern** — each `rec.pdf` value is a `data:application/pdf;base64,...` data URI inline in the `RECOMMENDATIONS` array (same file-size caveat as the CV PDFs above: don't read/grep across these lines naively, anchor edits on a short unique prefix of the payload, never hand-regenerate). This was originally built as separate `assets/recommandations/<id>.pdf` files (lighter, cacheable) but was deliberately switched to base64 at the user's explicit request, after being told this increases `index.html`'s size (~1.23MB total) rather than reducing it — the user prioritized the CV pattern's "more professional" single-embedded-file feel over the file-size tradeoff. **Preview images stay separate files**, `assets/recommandations/<id>-preview.jpg`, referenced by relative path — that part of the original reasoning (cacheable, independently-loadable, no benefit to inlining a growing set of images) still holds and wasn't part of the user's request.
- **Preview images** are static JPEGs (macOS `qlmanage -t` → `sips` resize/reformat, ~450–700px wide, ~45–65KB each) rendering the PDF's actual first page — not a generic "PDF icon" placeholder. They're pre-generated once per letter, not created at runtime (no PDF.js or similar dependency): if a letter is replaced, regenerate its preview the same way and overwrite the file.
- **Every quote is copied verbatim from the actual letter** — read directly from the PDF, never paraphrased, translated or invented (a hard requirement here: these are real people's names and words; the Long Arc quote stays in English because the letter is in English). `type`/`typeLabel` record what the letter was actually written for, not an assumption: KTM and BSB are addressed to a Master admissions committee (KTM grew out of a real internship, but the letter itself targets an academic application), so both are `academique`; the Long Arc letter (Hervé Labarge — the signature gives only "Long Arc Capital, New York", no job title, so none is shown) recommends Titouan "for internship opportunities", so it is `stage`, and it comes from someone Titouan only exchanged with, so there is no work-relationship wording anywhere.
  - **Transparency is per type, not global.** `RECO_DISCLOSURES` maps each `type` to its sentence, and the list render emits it as a `.reco-disclosure` note right before the first card of each run of same-typed letters — so the order in `RECOMMENDATIONS` matters (Long Arc first, then the two academic letters under their own note). The academic sentence is the user's exact wording and must stay verbatim. The old single `#reco-disclosure` element (shown/hidden via `.some(academique)`) no longer exists: one global line would have misdescribed the non-academic letter. The `.reco-list .reco-card:nth-of-type(n)` reveal-stagger rules use `nth-of-type`, not `nth-child`, precisely because those notes are `<p>` siblings between the `<article>` cards.
- **`recommendationCardHtml(rec)`** builds the full card (`.reco-card`, two-column grid: `.reco-text` left, `.reco-media` — preview + download — right); **`injectRecommendationPreview(rec)`** builds the compact Parcours version. Both go through `escapeHtml`/`escapeAttr` before touching `innerHTML`, even though the data is internally authored, not user input — defensive by default, matching the macro-bar tooltip's existing pattern.
- **Parcours integration is opt-in per experience via `rec.parcoursStep`** (the `data-step` index to target) — `injectRecommendationPreview` wraps that one `.p-panel`'s existing children in a new `.p-panel-body` div (untouched otherwise) and appends an `.p-reco` aside as a sibling, then adds the `.p-panel--with-reco` modifier class to the panel. Every other `.p-panel` is never touched, in markup or CSS, since none of them match `.p-panel--with-reco` — this was deliberately built so `#cell-levier`-style hand-editing of each experience is never needed. Only Bachelor (`parcoursStep: 0`) has a confirmed match right now (Jean-Christophe Cattane's letter is from BSB — Burgundy School of Business, the same school as that Parcours step); there is currently no experience on the timeline for the KTM letter, so `parcoursStep: null` there — don't guess a mapping for it. The Long Arc letter is likewise `parcoursStep: null` by explicit request (Titouan only exchanged with its author; it is not an experience).
- **`.p-panel--with-reco{display:flex}`** puts the wrapped `.p-panel-body` (`flex:0 1 620px`, matching every other panel's fixed reading width exactly) and `.p-reco` (`flex:0 1 220px`) side by side, with `max-width:none` on the panel itself (overriding the shared `.p-panel{max-width:620px}`) so the pair isn't squeezed into the old single-column cap. Both children use `flex:0 1 <basis>` (grow:0) rather than `flex:1`, so on a narrow desktop width they shrink together instead of one starving the other or overflowing — verified with no horizontal overflow down to a 920px-wide viewport (the layout only fully stacks at the existing `max-width:900px` Parcours fallback breakpoint, same as every other Parcours responsive behavior).
  - **Gotcha hit and fixed while building this**: the mobile/reduced-motion reset for `.p-panel--with-reco` was first added to the *existing* combined `@media (max-width:900px),(prefers-reduced-motion:reduce)` block (up near `.parcours-scroller`), but `.p-panel--with-reco`'s own base rule (`display:flex`, unconditional) was written *after* that block in the new Recommandations CSS — so per the site's documented "later in file wins regardless of media block" rule (see the section-rhythm gotcha above), the base rule kept winning even inside the media query, and the reco card rendered as a cramped side column on mobile instead of stacking. Fixed by adding a **second** occurrence of that same combined media query, positioned after the base rule, holding just the reset. This is the same class of bug the section-rhythm note warns about — it just hadn't previously bitten a *combined* query, only the plain `@media(max-width:680px)` one.

## Calculateur (Analyse financière)

`#calculateur` is a two-column shell (`.calc-shell` → `.calc-inputs` left, `.calc-results` right, same `.calc-group`/`.g-title` pattern on both sides) that recalculates everything on every `input` event — no submit button, nothing sent anywhere, nothing persisted. It was rebuilt from a small 7-ratio calculator into a fuller analysis covering performance, leverage, profitability, liquidity and cash-flow, plus a "Valorisation par comparables" module (see below); the section heading is "Valorisation" (was "Analyse financière", then renamed to match the nav drawer label — see the nav note above), not "Calculateur de ratios".

- **Data model**: `netDebt()` = Dette financière brute − Trésorerie (can be negative — a net cash position — and is displayed as such, never clamped or flagged); `freeCashFlow()` = EBITDA − Impôts − Capex − Variation du BFR − Intérêts. Both return `null` (never `0`, `NaN`, or a stale value) the moment any input they depend on is missing — `safeDiv(num, den)` centralizes the "missing or divide-by-zero → null" rule for plain ratios, and `growthRate(curId, prevId)` the same for the two YoY figures. A `0` a user actually typed is a real value, not a missing one — e.g. EBITDA = 0 with CA > 0 correctly renders Marge d'EBITDA as `0,0 %`, not `—`; it's only when the *denominator* is `0` (or either side is unfilled) that a ratio renders `—`.
- **All monetary fields are plain euros, not millions.** Every input's `.unit` label reads `€` (not `M€`), and `fmtEUR(n)` formats absolute-euro outputs (Dette nette, FCF, Enterprise Value, Equity Value, comparables EV/EBITDA) as a rounded whole-euro amount with `fr-FR` thousand-grouping, e.g. `150 000 €` — no decimals, since centimes aren't meaningful at company-aggregate scale. This was a deliberate switch from an earlier M€-only version: entering a real small-company figure like a 200 000 € CA into a field silently labeled `M€` would have been read as 200 000 M€ (200 milliards €), and the ratios (which are scale-invariant, num/den) would have looked fine while every absolute-euro output was off by 6 orders of magnitude. If a future edit ever reintroduces an `M€` label or a millions-based scale, check `fmtEUR` and all 15 `.unit` spans together — they must agree.
- **`setOut(id, text, cls)`** is the one place that writes a result and its color together, toggling `.warn` (red, `--neg`) / `.pos` (green, `--pos`) / neither on the cell's `.r-cell`, mirroring the `.m-delta`/`.delta-pos`/`.delta-neg` convention used on the analysis cards. Only Croissance CA and Croissance EBITDA get bidirectional coloring (`signClass` — green if positive, red if negative, neutral at exactly `0`), since they're the only two genuine period-over-period *variations*; every other ratio uses `negClass` (red only if negative — a margin/ROE/ROA turning negative is worth flagging, a positive one isn't a "move" worth coloring) or no color at all (leverage ratios, net debt, FCF, EV, Equity Value — a negative net debt or EV/Equity swing isn't inherently bad news, so it's shown plainly, not flagged).
- **Priority tiers** (`.r-cell.r-p1`/`.r-p2`/unmarked/`.r-p3` in the HTML) control *visual weight only*, not layout — all tiers share the same `.r-grid` two-column flow. `.r-p1` (Croissance EBITDA, Marge d'EBITDA, Dette nette/EBITDA, FCF, Enterprise Value, Equity Value) gets a `3px solid var(--bronze)` left border and a larger value (`25px` vs the base `22px`) — the same left-border-accent language already used for `.p-gap-phase`/`.phase` elsewhere, not a new motif. `.r-p3` (Marge nette, ROE, ROA, liquidité) just shrinks the value to `18px`/`500` weight. Which ratios land in which tier is a direct, deliberate mapping from the brief that added them — don't rebalance the tiers without being asked, the whole point is that the M&A-relevant ratios (leverage, cash generation, valuation) visually outrank the descriptive ones (ROE/ROA/liquidity) at a glance.
- **Interpretation text** (`.r-interp`, italic, under `.r-hint`) is static hardcoded copy for six ratios (Marge d'EBITDA, Dette nette/EBITDA, FCF, Conversion EBITDA→FCF, Enterprise Value, Equity Value) — short, deliberately hedged ("indique", "mesure"), never a verdict. Liquidité générale's is the one *dynamic* interpretation (`liquidityInterp(r)`, three tiers at `<1`, `1–1.5`, `>1.5`), recomputed and written into `#interp-liquidite` on every `recalc()` — if the liquidity thresholds ever change, they only live in that one function.
- **Valorisation is now "Valorisation par comparables"** (Comparable Companies Analysis), not a manually-entered multiple — that field (`in-multiple`) and the functions built on it (`enterpriseValue()`, `equityValue()`, the old `renderSensitivity()`/`#sens-body`) were removed entirely, not deprecated in place. The target's EBITDA and net debt are *reused* from the Performance/Structure financière fields above (`val('ebitda')`, `netDebt()`) — this section creates no new target-data inputs.
  - **Comparables table** (`#comps-body`): each row is plain DOM input elements (`#comp-name-<id>`, `#comp-ev-<id>`, `#comp-ebitda-<id>`), exactly like every other field in this calculator — there's no separate JS array holding typed values, the DOM *is* the source of truth. `compRows` (an array of row ids, from an incrementing `compSeq`) tracks only which rows exist and in what order. `addCompRow()`/`removeCompRow(id)` append or remove a single `<tr>` node directly — they never rebuild the whole `<tbody>` — specifically so that typing in one row's inputs, or adding/removing a different row, never disturbs another row's DOM node, value, or cursor focus. 1–5 rows (`updateCompsControls()` disables "+ Ajouter" at 5 and every `.comps-remove` button at 1); 3 seeded on load via `addCompRow()` in a loop, matching the panel's own stated minimum.
  - **Per-comparable multiple**: `readComps()` computes `ev/ebitda` per row, but only when EBITDA is strictly `> 0` — an EBITDA of `0` or negative renders `—` in that row's `.comps-multiple` cell *and* is excluded from the panel statistics entirely, never coerced to `Infinity`/`NaN` and never silently averaged in.
  - **Panel statistics** (Minimum/Médiane/Moyenne/Maximum) only compute once **≥3** comparables have a valid multiple (`readComps()` → filter → length check) — below that, `#comps-msg` ("Ajoutez au moins 3 sociétés comparables…") shows and `#comps-stats-block` hides, and every dependent output (target EV/Equity, the method table, the interpretation) falls back to its own empty/`—` state rather than computing from an incomplete panel. The **médiane** is the one tier-1 (bronze-accented) stat and the only one used to value the target — this is deliberate per the brief ("la médiane... servira de référence principale"); mean/min/max exist for the method table's range, not as alternate primary estimates.
  - **Target valuation**: Enterprise Value = target EBITDA × median multiple; Equity Value = EV − target net debt. Each is independently nullable — per the brief's own edge case, a missing net debt still lets EV compute, with only Equity Value falling back to `—`.
  - **Method table** (`#comps-method-body`, reuses the `.sens-wrap`/`.sens-table`/`.is-current` classes from the pre-existing sensitivity table rather than new ones): four rows, Minimum/Médiane/Moyenne/Maximum, each applying its own multiple to the *same* target EBITDA/net debt — this table simultaneously serves the brief's "valorisation selon plusieurs multiples" (§9) and "sensibilité de valorisation" (§10), which turned out to ask for identical rows/columns once multiples come from a panel instead of a manual ±2x sweep; there's deliberately only one table, not two duplicates, framed once as a valuation-by-method comparison and once as the "fourchette"/sensitivity lede line right above it.
  - **Interpretation** (`#comps-interp`, plain prose, not italic — distinct from the small `.r-interp` notes elsewhere) is generated fresh in `recalcComps()` from the live median/EV/Equity figures, never hardcoded; `#comps-caveat` right below it *is* static, constant text ("le choix du panel... peut avoir un impact significatif") and is meant to stay that way regardless of the numbers.
- **Mobile-overflow gotcha**: `.calc-inputs` and `.calc-results` are direct children of the CSS Grid `.calc-shell` and both need `min-width:0`. Without it, a grid item defaults to `min-width:auto`, which means it won't shrink below its content's intrinsic width — and since nothing between `.calc-results` and a wide descendant table resets that intrinsic-width contribution, the *whole page* stretched to ~499px on a 375px viewport even though that table's own `overflow-x:auto` wrapper was already in place and should have contained it locally. `overflow-x:auto` only stops content from overflowing *visually*; it doesn't, by itself, stop a wide descendant from inflating an ancestor grid item's automatic minimum size. This bit twice — once for the old sensitivity table (`.sens-table{min-width:420px}`), and the fix (`min-width:0` on both grid items) automatically covered the comparables table (`.comps-table{min-width:520px}`) when it was added later, since the fix lives on the shared ancestor rather than per-table. If a future addition anywhere inside `.calc-shell` needs another wide, horizontally-scrollable element, this is already handled — but check it stays that way if `.calc-inputs`/`.calc-results` are ever restructured.
- The `.calc-shell` two-column split collapses to one column at `900px` (not the site's usual `680px` — this section alone stacks a breakpoint earlier, in the same `@media(max-width:900px)` block used for `.util-ticker`/`.edc-grid`, because the results side is now dense enough that it needs the tablet range too), and `.r-grid` itself additionally drops from two columns to one at `680px` (in the *second*, later `@media(max-width:680px)` block, per the two-680px-blocks gotcha above) so individual result cards stay comfortable on a phone even though the shell already stacked earlier.

## Macro rates banner — second, independent financial strip

Right below `.util-bar` (the LVMH/Hermès TradingView ticker) sits `.macro-bar` (`#macro-track`/`#macro-updated`), a **separately built** banner showing five macro indicators in this fixed order (policy rates first, then the three 10Y government-bond yields): 🇪🇺 BCE (ECB deposit facility rate) · 🇺🇸 Fed (target range, e.g. "3,50–3,75 %") · 🇫🇷 OAT 10Y · 🇩🇪 Bund 10Y · 🇺🇸 Treasury 10Y. It is deliberately **not** a TradingView widget — the ticker-tape widget can't combine two symbols into one "X–Y %" cell (needed for the Fed range) and has no working symbol for a live ECB policy rate (verified by testing `ECONOMICS:`/`TVC:` symbols in the widget — they render an error icon; only `FRED:`-prefixed series resolve, and FRED has no ECB series). The two widgets are independent by design — editing one must never touch the other.

**All five indicators show the same `[flag] [label] [level] [arrow] [signed bps]` format** — level and delta are never treated differently per indicator; the *comparison period* behind the delta is the only thing that varies, and it's chosen per source rather than forced to a single window (see below).

Data sources (all public, official, keyless REST/CSV endpoints — verified to allow cross-origin `fetch()` from a browser, so nothing needs a backend or an exposed API key). Every fetcher resolves `{value, deltaBps}` — `value` a pre-formatted French-locale string (`fmtPct`/`fmtRange`), `deltaBps` a raw number of basis points or `null` if it genuinely couldn't be computed (never invented):
- **BCE**: ECB Data Portal, `data-api.ecb.europa.eu/service/data/FM/D.U2.EUR.4F.KR.DFR.LEV` (SDMX-JSON), daily — delta vs. the previous daily print (usually `0,0 bps`, since the deposit rate only moves on Governing Council decisions; that's correct, not a bug).
- **Fed**: New York Fed reference rates API, `markets.newyorkfed.org/api/rates/all/search.json?startDate=...&endDate=...&type=rate` (a 30-day lookback window, **not** the simpler `.../latest.json` used before it needed history) — `targetRateFrom`/`targetRateTo` are the FOMC's official target range; the delta compares the range **midpoint** against the previous business day's entry (both bounds move together at a decision, so midpoint deltas track the real move). Same "usually `0,0 bps` between FOMC meetings" logic as BCE.
- **OAT 10Y** / **Bund 10Y**: same ECB Data Portal dataset, `.../IRS/M.FR.L.L40.CI.0000.EUR.N.Z` and `.../IRS/M.DE.L.L40.CI.0000.EUR.N.Z` (France vs. Germany) via the shared `fetchECBWithDelta(seriesPath)` — both request `lastNObservations=2` and diff them (`parseSDMXLastTwo`). This specific ECB series is **monthly**, so both the level and the delta can lag up to ~6 weeks; that's an ECB statistical-series limitation, not a bug. OAT deliberately reuses Bund's exact source/mechanism (added later, on request, to stay consistent with it) rather than a separate one.
- **Treasury 10Y**: `home.treasury.gov/.../daily-treasury-rates.csv/<year>/all?type=daily_treasury_yield_curve&...&_format=csv` — the year's full CSV is already being fetched for the `"10 Yr"` column of the latest row, so the delta is read from the **next** row (previous business day) in the same response; no second request.

Each fetch is independent and wrapped so a failure renders `N/D` for just that one item (`.macro-value.is-na`, no delta shown at all) instead of breaking the banner. A *narrower* failure — the level loaded fine but the delta specifically couldn't be computed (e.g. only one observation came back) — renders the level normally with a neutral `— —` in place of the arrow/bps (`fmtDeltaBps` returns this whenever `deltaBps` isn't a finite number); this is a different, milder case than the whole-item `N/D` and the two must not be conflated. `#macro-updated` shows a "Mis à jour à HH:MM" timestamp (hidden on mobile, `max-width:680px`, to save space) and data refreshes every 15 minutes via `setInterval` while the tab stays open. The scrolling marquee is a plain CSS `@keyframes` (`macro-scroll`, translateX 0 → −50%) over content duplicated once in `render()` — not a TradingView animation — chosen so the items never wrap to a second line and scroll smoothly at any width.

**`fmtDeltaBps(bps)`** (right after `fmtPct`/`fmtRange`) is the single place all five deltas are formatted, so they can never visually diverge: it rounds to one decimal first (`Math.round(bps*10)/10`) and *then* decides sign/arrow/color from the rounded value — not the raw one — so a delta that rounds to zero (e.g. `+0.02`) always renders as the neutral `→ 0,0 bps` rather than a stray `+0,0 bps` in green. Three states, one function: positive → `↑`/`.delta-pos` (green, `--pos`); negative → `↓`/`.delta-neg` (red, `--neg`); zero or uncomputable → `→`/`— —` respectively, both `.is-neutral` (muted, same tone as `.macro-value.is-na`). `.delta-pos`/`.delta-neg` are the same classes already used for the `.m-delta` badges on the analysis cards — reused deliberately, not reinvented. `render()` only adds a `title` tooltip when `item.tooltip` is set (currently just OAT) and only skips the delta badge entirely when the whole item is `N/D` — every other aspect of the markup (font size, spacing, animation) is identical across all five, by construction (one shared `render()` loop, no indicator gets special-cased CSS).
